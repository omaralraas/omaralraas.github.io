Incident Response: RedLine Lab

Lab Name RedLine Lab
Provider CyberDefenders
Category Host Memory Forensics & Malware Triage
Tools Volatility 3, Volatility 2, WSL / Strings

Executive Summary

A Windows workstation was compromised after an employee downloaded what appeared to be an installer package. Security monitoring noticed suspicious outbound telemetry, but the local Network Intrusion Detection System (NIDS) failed to trigger any high-severity perimeter alerts.

As part of the Blue Team response, a physical memory dump (MemoryDump.mem) was acquired for forensic analysis. Using Volatility 3, I reconstructed the full intrusion lifecycle:

  1. Initial Staging: The victim browsed a malicious delivery endpoint masquerading as a gaming repository and dropped a binary (oneetx.exe) into the user's temporary directory.
  2. Process Injection: Upon execution, the malware allocated memory with dangerous PAGE_EXECUTE_READWRITE permissions and spawned a hollowed rundll32.exe child process.
  3. NIDS Evasion Mechanism: The host utilized an active Outline VPN connection (Shadowsocks proxy), encapsulating and encrypting all C2 traffic through a local virtual interface (tun2socks.exe), thereby blinding the perimeter NIDS.
  4. Threat Attribution: Memory string analysis linked the command-and-control communication back to known infrastructure distributing the Redline Stealer malware family.

Environment & Forensic Tooling

Evidence provided:

  • MemoryDump.mem — 2 GB raw physical RAM image from the compromised Windows workstation.

Tooling Strategy & The Modern Windows 10 Hurdle:

Legacy tools like Volatility 2.6 scan raw memory searching for an unencrypted KDBG structure (_KDDEBUGGER_DATA64). On modern Windows 10 builds (Build 19041+), Microsoft encodes and encrypts this block, causing Volatility 2's imageinfo plugin to fail with No suggestion.

To overcome this, the investigation leveraged Volatility 3, which bypasses static profile scanning by dynamically resolving kernel symbols (ntkrnlmp.pdb) directly from Microsoft Symbol Servers.

Phase 1

Operating System Baselines & Symbol Resolution

Determining the kernel base and OS architecture is essential for mapping subsequent virtual memory structures:

vol.exe -f MemoryDump.mem windows.info

Volatility 3 automatically fetched the appropriate PDB symbol package (68A17FAF3012B7846079AEECDBE0A583-1) and surfaced the system configuration:

  • Operating System: Windows 10 (Build 10.0.19041, 64-bit)
  • Acquisition Timestamp: 2023-05-21 23:02:39 UTC
  • Kernel Base: 0xf8076221a000
Phase 2

Process Hierarchy Triage & Rogue Hunting

Examining the hierarchical process tree (pstree) allows analysts to spot execution anomalies that would otherwise blend in when viewing flat process lists:

vol.exe -f MemoryDump.mem windows.pstree

1. The Rogue Stager (oneetx.exe)

Analyzing the user session under explorer.exe revealed a process running from an unusual directory path:

PID   PPID  ImageFileName  Path
5896  8844  oneetx.exe     \Device\HarddiskVolume3\Users\Tammam\AppData\Local\Temp\c3912af058\oneetx.exe

Legitimate Windows binaries reside in C:\Windows\System32 or C:\Program Files. A binary executing out of a subfolder within AppData\Local\Temp\ is a classic indicator of a dropped payload.

Answer to Q1 (Suspicious Process): oneetx.exe

Answer to Q7 (Full Path): C:\Users\Tammam\AppData\Local\Temp\c3912af058\oneetx.exe

2. Child Process Spawning (rundll32.exe)

Looking directly beneath oneetx.exe in the tree hierarchy revealed a child process spawned at 22:31:53 UTC:

5896  8844  oneetx.exe    ...
* 7732  5896  rundll32.exe  \Device\HarddiskVolume3\Windows\SysWOW64\rundll32.exe

Malware authors routinely spawn native Windows utilities like rundll32.exe as a sacrificial process to hollow out and inject code into (Living-off-the-Land).

Answer to Q2 (Child Process): rundll32.exe

Phase 3

In-Memory Code Injection & Memory Protection

To confirm whether oneetx.exe performed in-memory unpacking or process injection, I audited the process's Virtual Address Descriptors (VAD) using windows.malfind:

vol.exe -f MemoryDump.mem windows.malfind --pid 5896

The plugin flagged a suspicious memory allocation:

PID   Process     Start VPN  End VPN    Tag   Protection              Notes
5896  oneetx.exe  0x400000   0x437fff   VadS  PAGE_EXECUTE_READWRITE  MZ header

Hexdump:
4d 5a 90 00 03 00 00 00 04 00 00 00 ff ff 00 00  MZ..............
b8 00 00 00 00 00 00 00 40 00 00 00 00 00 00 00  ........@.......

Forensic Analysis:

  • Protection Violation: Operating systems enforce Write XOR Execute (W^X) policies. An unbacked memory page flagged with PAGE_EXECUTE_READWRITE (RWX) indicates code was written into RAM and immediately prepared for dynamic execution.
  • PE Artifacts: The memory region begins with 4D 5A (the classic DOS MZ magic header), proving an unmapped executable or reflective loader was loaded in memory.

Answer to Q3 (Memory Protection): PAGE_EXECUTE_READWRITE

Phase 4

Network Connections & Dissecting the NIDS Bypass

To identify the C2 infrastructure and explain why the network intrusion detection system was bypassed, I ran windows.netscan:

vol.exe -f MemoryDump.mem windows.netscan

1. The Attacker C2 IP

Filtering network sockets by the malicious process PID (5896) revealed an outbound connection on port 80:

Proto  Local Address     LocalPort  Foreign Address  ForeignPort  State   PID   Owner
TCPv4  10.0.85.2         55462      77.91.124.20     80           CLOSED  5896  oneetx.exe

Answer to Q5 (Attacker IP): 77.91.124.20

2. Uncovering the NIDS Evasion Vector

Looking further through the active process tree and network sockets revealed an interesting architecture:

6724  3580  Outline.exe    \Program Files (x86)\Outline\Outline.exe
* 4628  6724  tun2socks.exe  ...third_party\outline-go-tun2socks\win32\tun2socks.exe

How the bypass functioned:

  • Outline is an open-source VPN solution built on the Shadowsocks protocol.
  • The internal process tun2socks.exe intercepted all IP traffic from the endpoint and routed it into an encrypted tunnel.
  • Because the cleartext HTTP connection between oneetx.exe and 77.91.124.20 was encapsulated inside encrypted VPN traffic, the perimeter NIDS could not inspect packet payloads or match signatures against known malicious C2 patterns.

Answer to Q4 (VPN Process): Outline.exe

Phase 5

Payload Delivery & Threat Attribution

With the external IP 77.91.124.20 identified, I searched the physical memory dump for associated HTTP request logs, referrer headers, and URLs:

strings -a MemoryDump.mem | grep -i "77.91.124.20" | grep -i "\.php"

This surfaced the delivery URL visited on the remote host:

http://77.91.124.20/store/games/index.php

Answer to Q6 (PHP URL): http://77.91.124.20/store/games/index.php

Malware Attribution: Cross-referencing the landing page structure (/store/games/index.php) and C2 endpoint with threat intelligence records confirms the payload as Redline Stealer. The threat actor distributed the malware disguised as cracked video games or cheats to harvest saved browser credentials, autocomplete data, credit cards, and cryptocurrency wallets from the victim.

Key Takeaways

Modern Windows 10 Demands Volatility 3

Windows 10 Build 19041+ encodes kernel debugger blocks (KDBG), breaking legacy Volatility 2 profile scanners. Volatility 3's dynamic PDB symbol retrieval is essential for modern triage.

Encrypted Tunnels Blind Perimeter Defenses

Signature-based NIDS appliances cannot inspect traffic tunneled through client-side VPNs like Outline/Shadowsocks. Robust security architectures require host-based EDR telemetry to detect anomalous socket creation before tunnel encapsulation occurs.

RWX Permissions are High-Fidelity IOCs

Legitimate Windows binaries strictly adhere to DEP/W^X. In-memory virtual allocations marked PAGE_EXECUTE_READWRITE paired with MZ headers or shellcode loops are definitive indicators of in-memory execution.
