CTF Write-up: Prioritise (TryHackMe)

PlatformTryHackMe
Category🕸️ Web Exploitation
DifficultyMedium
TagsSQL Injection · ORDER BY · Blind SQLi · SQLite

Challenge Overview

Objective: Exploit a less common SQL injection vector in a to-do list application that lets users sort tasks by priority.

"A simple task manager where you can create to-dos and order them by priority. Sometimes the most overlooked parameters hide the most dangerous bugs."

This room focuses on a frequently overlooked injection surface: the ORDER BY clause. Instead of the usual input fields, the vulnerability lives in the sorting parameter — the one thing most testers scroll right past.

Methodology

STEP 1 Initial Assumption — Testing the INSERT Endpoint (Failed)

The application exposes a "create new task" form that submits to POST /new with title and date parameters. This felt like the natural injection point, so I pointed sqlmap at it.

sqlmap -u "http://TARGET/new" --data="title=test&date=2026-01-01" --batch
✗ FAILED — Every successful payload was an INSERT statement, flooding the database with hundreds of todo items. The box became unresponsive and started returning 500 errors and timeouts.

This was a classic mistake: running sqlmap against an INSERT endpoint without limiting requests. Each injected payload created a new row, eventually overwhelming the fragile CTF machine. Lesson learned the hard way.

STEP 2 Pivoting — Re-reading the Room Description

After the machine recovered, I stepped back and re-read the room description carefully. The key phrase was: "order our tasking based on priority."

Looking at the main page, I noticed the application accepted a GET parameter to control sorting:

/?order=title
/?order=date

This is a textbook ORDER BY injection point — the user-supplied value is placed directly into the SQL query's sorting clause. It's less commonly tested because most scanners and tutorials focus on WHERE clause injections.

STEP 3 Confirming the Injection — Boolean Oracle via CASE

To confirm the parameter was injectable, I used a conditional CASE expression that would change the sort order depending on a true/false condition:

?order=(CASE WHEN 1=1 THEN title ELSE date END)
?order=(CASE WHEN 1=2 THEN title ELSE date END)
✓ CONFIRMED — The order of displayed tasks changed depending on the condition. When the condition was true (1=1), tasks sorted by title; when false (1=2), they sorted by date.

This gave us a boolean-based blind SQL injection oracle: we can ask the database any yes/no question by observing whether the page sorts by title or date.

STEP 4 Database Fingerprinting

Using the boolean oracle, database fingerprinting confirmed the backend was running SQLite. This was important because SQLite has specific syntax quirks — for instance, it doesn't support SLEEP() for time-based attacks, and heavy operations like RANDOMBLOB() kept crashing the service.

STEP 5 Exploitation with sqlmap

With the injection point confirmed and the DBMS identified, I ran sqlmap with carefully tuned parameters to avoid killing the box again:

sqlmap -u "http://TARGET/?order=title" -p order \
  --batch --dbms=sqlite --technique=B --threads=1

Key flags explained:

  • -p order — Target only the order parameter
  • --technique=B — Boolean-based blind only (no time-based attacks that would crash the service)
  • --threads=1 — Single thread to be gentle on the fragile CTF box
  • --dbms=sqlite — Skip fingerprinting overhead since we already know the backend

sqlmap successfully identified the injection and began enumerating the database. Two tables were found:

Database: SQLite
[2 tables]
+-------+
| todos |
| flag  |
+-------+

STEP 6 Flag Retrieval

Dumping the flag table was straightforward:

sqlmap -u "http://TARGET/?order=title" -p order \
  --batch --dbms=sqlite --technique=B --threads=1 \
  -T flag --dump

Key Takeaways

🔍 Always Test Sorting Parameters

ORDER BY injection points are frequently overlooked because most testing focuses on WHERE clauses and form inputs. Any parameter that controls sorting, grouping, or column selection is a potential injection surface.

⚠️ INSERT Endpoints Will Flood the Database

Running sqlmap against an INSERT endpoint without rate limiting or cleanup will create hundreds of rows per scan. On fragile CTF boxes, this can make the machine unresponsive. Always understand what SQL operation your target endpoint performs before unleashing automated tools.

🐢 Be Gentle with CTF Infrastructure

On shared or single-instance CTF boxes, stick to boolean-based techniques and low thread counts. Time-based payloads using heavy operations (like RANDOMBLOB in SQLite) can crash the service entirely. Use --technique=B --threads=1 when in doubt.

🧠 The CASE Expression Trick

Using CASE WHEN condition THEN column_a ELSE column_b END in an ORDER BY clause is a powerful technique to turn sort order into a boolean oracle. If the page renders differently based on the condition, you have blind SQLi — no error messages needed.
