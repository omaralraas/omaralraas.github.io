Incident Response: Wayne & Stark Enterprises

Challenge l337 S4uc3 (GrrCon 2013)
Category Network & Memory Forensics
Tools TShark (Wireshark CLI), Volatility 2.6

Executive Summary

Wayne and Stark Enterprises suffered a breach of a critical development asset, development.wse.local, resulting in the theft of top-secret weapon designs. The incident began with an IDS alert flagging active malware on the internal network.

Using network traffic analysis (PCAP) and host-based memory forensics, I reconstructed the full attack chain:

  1. Initial infection: An internal Windows client was compromised by the Zeus banking trojan.
  2. Web server exploitation: The Ubuntu web server (development.wse.local) was breached via a vulnerable phpMyAdmin instance, giving the attacker a Metasploit Meterpreter reverse shell.
  3. Data theft: The attacker pivoted to a password-protected WordPress directory and exfiltrated confidential blueprints.

Environment & Tooling

Evidence provided:

  • IR-Alert.png — IDS dashboard screenshot
  • GrrCON.pcapng — Full network capture
  • webserver.vmss — VMware suspended-state memory dump

Tools used:

  • TShark: Used for packet filtering, TCP stream reassembly, and protocol analysis.
  • Volatility 2.6: Chosen over Volatility 3 for its mature support and simpler custom-profile generation on this older Ubuntu 10.04 kernel.
  • Custom Volatility profile: The memory image was paired with a DFIRwebsvr.zip containing System.map-2.6.32-38-server and module.dwarf. Dropping this into Volatility 2's --plugins directory generated a working LinuxUbuntux64 profile on the fly.
Phase 1

Infrastructure & Timeline Mapping

Public IP of the web server

tshark -r GrrCON.pcapng -Y "http.request" -T fields -e ip.dst -e http.host

Isolating HTTP requests for development.wse.local showed the host consistently resolving to a single public IP. Answer: 74.204.41.73

Capture start time

tshark -r GrrCON.pcapng -T fields -e frame.time_epoch -c 1

Frame 1 carries epoch timestamp 1378853467.894237000 → 2013-09-10 22:51:07 UTC. Converting to EST (UTC-4 at the time of capture) for consistency with later timeline questions: Answer: 18:51:07 EST

LAN gateway

tshark -r GrrCON.pcapng -Y "arp" -c 20

172.16.0.1 repeatedly issued ARP "who-has" broadcasts and resolved to a WatchGuard MAC address (00:90:7f:80:9e:b9) — consistent with a WatchGuard firewall/gateway appliance. Answer: 172.16.0.1

Phase 2

Malware Infection Analysis (Zeus)

Malware identification and connectivity check

The IR-Alert.png IDS dashboard showed a triggered signature: ET TROJAN Zeus Bot GET to Google checking Internet connectivity, with the destination IP visible in the IP header panel.

  • Malware: Zeus
  • Connectivity-check destination: 74.125.225.112

CNC infrastructure and staging files

tshark -r GrrCON.pcapng -Y "http.request and ip.src == 172.16.0.109" \
  -T fields -e frame.number -e ip.dst -e http.request.method -e http.request.uri

The infected host (172.16.0.109) reached out to 88.198.6.20 in three stages:

  1. Frame 3472: GET /NewDesign.jpg.exe (Dropper payload)
  2. Frame 3510: GET /bt.exe (Zeus loader/executable)
  3. Frame 3609: GET /cf.bin (Binary configuration file)

Repeated POST /gt.php requests followed, confirming ongoing C2 check-ins.

  • CNC IP: 88.198.6.20
  • Config file: cf.bin
  • Launch executable: bt.exe
Phase 3

Web Server Compromise

Service fingerprinting

tshark -r GrrCON.pcapng -z follow,tcp,ascii,117

Following a standard 200 OK response revealed the server banners directly in the HTTP headers.

  • PHP version: 5.3.2 (X-Powered-By: PHP/5.3.2-1ubuntu4.20)
  • Apache version: 2.2.14 (Server: Apache/2.2.14 (Ubuntu))

WordPress credential capture

tshark -r GrrCON.pcapng -Y "http.request.method == POST and http.request.uri contains "wp-login"" \
  -T fields -e frame.number -e urlencoded-form.value

Frame 4282 (~18:56 EDT) captured a login POST to /wp-login.php for user Jsmith, with the plaintext password sent in the clear. Answer: wM812ugu

Protected design page access

tshark -r GrrCON.pcapng -Y "http.request.method == POST and http.request.uri contains "wp-pass""

The attacker bypassed a second layer of protection by posting the password 1qBeJ2Az to /wp-pass.php (frame 5743), then successfully loaded the protected page /wp/blog/?p=3 in frame 5747.

Frame 5747 timestamp: 1378854244.032499000 → 23:04:04 UTC. Answer: 19:04:04 EST

phpMyAdmin exploitation token

tshark -r GrrCON.pcapng -Y "frame.number == 3897" -T fields -e urlencoded-form.key -e urlencoded-form.value

Frame 3897 contains the malicious POST to /pma/index.php (phpMyAdmin) carrying the exploit token. Answer: b7aad621db97d56771d6316a6d0b71e9

Shellcode delivery

tshark -r GrrCON.pcapng -Y "udp.port == 31708" -T fields -e ip.src -e udp.srcport

IDS signature GPL SHELLCODE x86 inc ebx NOOP pointed to UDP payload delivery on destination port 31708. Tracing the stream back to its source port. Answer: 39709

Post-exploitation tooling

tshark -r GrrCON.pcapng -Y "frame.number == 5304" -T fields -e http.user_agent

The attacker downloaded unimportant.tar.gz from the compromised host; the User-Agent string on that request identified the tool used (Wget/1.13.4 (linux-gnu)). Answer: Wget

Kernel fingerprint via Meterpreter

tshark -r GrrCON.pcapng -z follow,tcp,ascii,155

TCP stream 155 carries the live Meterpreter session on port 4444. Carving strings from the stream surfaced the output of a sysinfo command. Answer: 2.6.32-38-server

Phase 4

Host-Based Memory Forensics

With the custom LinuxUbuntux64 profile generated, webserver.vmss was analyzed directly.

Process tree — shell spawns

vol.exe --profile=LinuxUbuntux64 -f webserver.vmss linux_pslist

The process list showed an apache2 worker (PID 1042) spawning a shell (sh, PID 1274), which in turn spawned a second shell (sh, PID 1275) — a classic web-shell-to-command-shell escalation chain.

  • Shell binary path: /bin/sh
  • Parent PID: 1042

Memory-mapped binary for PID 1274

vol.exe --profile=LinuxUbuntux64 -f webserver.vmss linux_proc_maps -p 1274

The first executable memory segment (0x0000000000400000) for PID 1274 mapped to /bin/dash, the actual binary behind Ubuntu's /bin/sh symlink. Answer: /bin/dash

Scheduler latency metric

The latency_record_count field in the process's task_struct is a scheduler-tracing counter that stays at its default of 0 unless latency debugging is explicitly enabled. Answer: 0

Carving a queued network packet

vol.exe --profile=LinuxUbuntux64 -f webserver.vmss linux_pkt_queues -D ./out
Get-FileHash -Algorithm MD5 .\out\receive.1105.3

linux_pkt_queues carved pending per-process packet queues directly from the memory image to disk. Hashing the extracted receive.1105.3 file produced its MD5 fingerprint. Answer: 184c8748cfcfe8c0e24d7d80cac6e9bd

Key Takeaways

Dual-vector compromise

The incident combined a client-side malware infection (Zeus) with an independent server-side web application exploit (phpMyAdmin), a reminder that IR investigations shouldn't assume a single attack path even when one IDS alert dominates the timeline.

Plaintext credentials over HTTP

Made both the WordPress compromise and the phpMyAdmin exploit trivial to reconstruct from the packet capture — a strong argument for enforcing HTTPS end-to-end, including on internal/admin interfaces.

Memory forensics closed the loop

Volatility confirmed the exact process lineage (apache2 → sh → sh) and recovered an in-flight network packet directly from RAM, uncovering details that packet capture alone couldn't.
